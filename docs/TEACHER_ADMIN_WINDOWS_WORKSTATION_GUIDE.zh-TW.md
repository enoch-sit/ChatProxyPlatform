# 教師與管理者 Windows Docker Desktop 工作站使用指南

本文件以教師、課程管理者與校內 IT 支援人員為主要讀者，說明 ChatProxy Platform 的整體用途、核心服務、Windows Docker Desktop 工作站部署方式，以及日常操作重點。

本文刻意避免過多開發細節，重點放在「這個系統是做什麼的」、「如何在 Windows 工作站啟動」、「教師如何在課堂中使用」，以及「當目標是約 100 位學生同時使用時，應如何規劃」。

---

## 1. 系統用途總覽

ChatProxy Platform 是一套把 AI 對話流程、身分驗證、權限管理與額度控管整合在一起的教學平台。它的設計目的不是只讓學生直接連到單一聊天機器人，而是讓學校或老師可以在受管理的環境中提供 AI 對話服務。

對教師與管理者而言，這套系統的價值在於：

- 可以限制只有已授權的使用者登入。
- 可以依角色區分管理者、教師與學生。
- 可以控管學生可使用的 AI 額度。
- 可以把前台聊天介面與後台 Flowise 流程設計分開管理。
- 可以先在 Windows 工作站用 Docker Desktop 快速部署，再視需要轉往 AWS 擴充。

---

## 2. 系統由哪些部分組成

整體系統可分成 5 個主要服務：

| 元件 | 主要用途 | 典型使用者 |
|------|----------|------------|
| Bridge | 提供學生與教師使用的聊天前台介面 | 教師、學生 |
| Flowise Proxy | 負責把聊天請求導向 Flowise，並協調驗證與額度檢查 | 系統內部服務 |
| Auth Service | 處理登入、權限、JWT 驗證與使用者身分 | 管理者、系統 |
| Accounting Service | 管理額度、扣點、使用記錄 | 管理者、系統 |
| Flowise | AI 流程設計與執行引擎 | 教師、管理者、技術人員 |

可以把它理解成以下流程：

1. 使用者先在 Bridge 前台登入。
2. Auth Service 驗證帳號密碼並發出登入權杖。
3. 使用者送出聊天問題後，Bridge 會把請求交給 Flowise Proxy。
4. Flowise Proxy 先確認權限與額度是否足夠。
5. 驗證通過後，再把請求送到 Flowise 執行 AI 流程。
6. 系統回傳回答，同時由 Accounting Service 記錄使用情況。

換句話說，Flowise 負責「生成回答」，而 Auth Service 與 Accounting Service 負責「誰可以用」以及「用了多少」。

## 3. 為什麼需要 Bridge 與 Flowise 分開

很多學校初看會以為只要部署 Flowise 即可，但本專案加入 Bridge 與 Proxy 層，目的是把教學現場的管理需求補齊。

- Flowise 適合做 AI 流程設計與模型串接。
- Bridge 提供較適合一般師生使用的前台入口。
- Proxy 層讓系統能在送出 AI 請求前先做登入驗證、權限檢查與額度控管。
- Auth 與 Accounting 則讓學校能以制度化方式管理帳號與資源。

如果只有 Flowise，本身並不等於完整的校園教學平台；加上 Bridge、Auth、Accounting 與 Proxy 後，才比較接近可管理的教學服務。

## 4. Windows Docker Desktop 工作站部署模式

### 4.1 這種部署模式適合什麼情境

Windows 工作站部署模式是指：

- 使用一台 Windows 10 或 Windows 11 電腦。
- 在該電腦安裝 Docker Desktop。
- 讓各個服務以 Docker 容器方式在同一台機器上運行。

此模式適合：

- 課前測試
- 教師個人備課
- 小規模示範
- 校內概念驗證
- 功能驗收與流程演練

此模式的優點：

- 建置快
- 容易搬遷與重建
- 不需要先建立完整雲端基礎設施
- 適合先讓教師熟悉系統

此模式的限制：

- 屬於單機部署，可靠性受單一工作站影響。
- 效能受該 Windows 電腦的 CPU、記憶體與磁碟速度限制。
- 若要穩定面向大量同時上線使用者，仍需要壓力測試與容量規劃。

## 5. 建議的 Windows 工作站基本條件

依照目前專案文件，部署前至少應具備：

- Windows 10 或 Windows 11
- Docker Desktop
- Python 3
- Git
- 建議 8 GB 以上記憶體
- 建議 20 GB 以上可用磁碟空間

若部署目的是實際課堂使用，而非單純測試，建議提高到更高規格，例如：

- 16 GB 以上記憶體
- 多核心 CPU
- SSD 儲存
- 穩定的校園網路

這些是實務建議，不代表目前 repo 已對單機 100 人同時在線完成正式效能驗證。

## 6. Windows 工作站的標準安裝流程

### 6.1 建議的安裝方式

本專案在根目錄提供三個主要 PowerShell 腳本：

- `setup.ps1`：首次安裝與啟動
- `patch.ps1`：更新與重建
- `diagnose.ps1`：健康檢查與故障排除

第一次在 Windows 工作站部署時，建議由系統管理者在專案根目錄執行：

```powershell
.\setup.ps1
```

這個流程會處理的事情包括：

- 檢查 Docker、Node、Git 等必要工具
- 產生 secrets 與各服務的 `.env` 設定
- 依相依順序啟動服務
- 執行健康檢查

### 6.2 啟動後的重要入口

本機部署完成後，常見入口如下：

| 功能 | URL |
|------|-----|
| Bridge 使用者前台 | http://localhost:3082 |
| Flowise Proxy API | http://localhost:8000 |
| Auth Service | http://localhost:3000 |
| Accounting Service | http://localhost:3001 |
| Flowise 管理介面 | http://localhost:3002 |
| MailHog 郵件測試介面 | http://localhost:8025 |

一般教師與學生主要接觸的是 Bridge；Flowise 管理介面通常由管理者、教師或技術支援人員使用。

### 6.3 安裝後如何確認系統正常

可執行：

```powershell
.\diagnose.ps1 -Quick
```

若需要完整檢查，可執行：

```powershell
.\diagnose.ps1
```

系統會檢查：

- Docker daemon 是否正常
- 容器是否有啟動
- 主要服務健康檢查網址是否回應
- 常用連接埠是否被占用

## 7. 教師與管理者的日常使用方式

### 7.1 教師平常會接觸哪些部分

對大多數教師來說，日常操作通常包含：

- 使用 Bridge 前台測試學生看到的聊天體驗
- 使用 Flowise 管理聊天流程或教學用 chatflow
- 與管理者合作建立學生帳號
- 確認學生額度是否足夠
- 課前確認系統健康狀態

### 7.1.1 教師或管理者如何在 Flowise 查看 chatflow

若教師或管理者需要確認教學用 AI 流程是否存在、是否能進一步編輯，可在 Flowise 管理介面依照以下方式查看：

1. 進入 Flowise 管理介面。
2. 在 `Agentflows` 頁面確認目前可用的流程清單。
3. 點開指定流程後，可進入畫布檢視該 chatflow 的節點與連線設計。

畫面 1: 在 `Agentflows` 頁面查看目前可用的流程。

![教師或管理者在 Flowise 查看 Agentflows 清單](images/flowise_teacher_01_agentflows.png)

畫面 2: 進入流程畫布，查看 chatflow 的節點與流程連線。

![教師或管理者在 Flowise 查看 chatflow 畫布](images/flowise_teacher_02_agentcanvas.png)

### 7.2 管理者平常會接觸哪些部分

管理者或校內 IT 支援通常會負責：

- 啟動或重啟工作站上的整套服務
- 建立與維護帳號
- 分配教師與學生額度
- 執行更新
- 故障時執行診斷

### 7.2.1 管理者如何查看學生 chatflow 對話紀錄

若管理者需要查看學生實際使用某個 chatflow 的對話內容，可在 Bridge 管理後台依照以下路徑操作：

1. 先登入 Bridge，並進入左側的 `Administration`。
2. 在管理頁面中切換到 `Student Chats` 分頁。
3. 在左欄選取要查看的學生帳號。
4. 在中間欄位選取該學生的某一個對話 session。
5. 右欄就會顯示該次學生對話內容，管理者也可以使用 `Export .txt` 匯出。

步驟 1: 進入管理後台主頁。

步驟 2: 切換到 `Student Chats` 分頁。

![管理者切換到 Student Chats 分頁](images/bridge_admin_student_chats_02_tab.png)

步驟 3: 選取要查看的學生帳號。

![管理者選取學生帳號以查看 session 清單](images/bridge_admin_student_chats_03_student_selected.png)

步驟 4: 開啟學生的對話 session，查看 chatflow 對話內容。

![管理者開啟學生 session 並查看對話內容](images/bridge_admin_student_chats_04_session_open.png)

### 7.3 學生的使用路徑

學生一般不需要接觸 Flowise 或後台服務，只需要：

1. 進入 Bridge 前台。
2. 使用學校提供的帳號登入。
3. 選擇可用的聊天流程或對話功能。
4. 開始提問。

這種前後台分離的做法，能降低學生直接接觸系統設定的風險。

## 8. 帳號、角色與額度的概念

依目前專案結構，可將角色理解為三類：

- 管理者：擁有最高管理權限
- 教師或督導角色：可協助管理學生、查看資料或分配資源
- 學生或一般使用者：主要進行對話與學習活動

額度系統的重點在於：

- 系統可記錄使用者剩餘額度
- 在送出 AI 請求前先檢查額度
- 請求完成後可扣除相應資源
- 管理者可調整教師與學生的配額

對教學現場而言，這代表學校可以：

- 控制每位學生的可用資源
- 避免少數帳號過度消耗 AI 用量
- 依課程需要設定不同班級或角色的使用政策

## 9. 建議的課前操作流程

若此平台要用於課堂前準備，建議教師或管理者依序檢查：

1. Docker Desktop 已啟動。
2. `setup.ps1` 建立的服務仍在執行。
3. `http://localhost:3082` 可正常開啟。
4. 至少用一組教師帳號完成登入測試。
5. 至少以一組學生帳號完成聊天測試。
6. 確認學生額度尚未耗盡。
7. 若本機還需對外提供服務，確認 Windows 防火牆與校內網路路由已設定完成。

如果只是本機測試，`localhost` 即可；如果要讓同一個教室或校內其他電腦連線，則還需要處理：

- 工作站的固定 IP 或 DNS 名稱
- 防火牆放行
- 反向代理或 TLS 憑證
- 校內網段存取規則

這部分已超出單純本機啟動範圍，通常需要 IT 支援協助。

## 10. 當目標是約 100 位學生同時使用時，應如何理解 Windows 工作站部署

這是最需要先說清楚的一點。

目前專案文件已完整描述 Windows Docker Desktop 的部署流程，但沒有提供「單一 Windows 工作站已正式驗證可穩定承載約 100 位學生同時在線」的基準測試結果。因此，在規劃時應把以下兩件事分開看：

### 10.1 Windows 工作站模式

適合：

- 前期試行
- 小規模班級
- 教學展示
- 課程開發與驗證

優勢：

- 快速建置
- 維運簡單
- 成本低

風險：

- 單點故障
- 當多位學生同時送出請求時，工作站資源容易成為瓶頸
- 若外部 AI 模型回應速度波動，整體體驗會一起受影響

### 10.2 約 100 位學生同時在線的規劃建議

若目標是「穩定服務約 100 位學生同時使用」，比較務實的做法是：

1. 先用 Windows 工作站完成功能驗證與教師流程演練。
2. 針對預計使用的 chatflow 做壓力測試。
3. 若要提供正式課堂或跨班大量使用，優先評估 AWS 部署。

AWS 架構的優點包括：

- 可用負載平衡與自動擴充
- 服務不是綁在單一教室電腦上
- 資料庫與監控能力較完整
- 對跨班級、多時段或大量同時連線更穩定

因此，本文件建議的定位是：

- Windows Docker Desktop 工作站：適合部署、測試、示範、教學準備
- AWS：較適合要穩定承接較高併發量的正式服務

如果學校堅持從 Windows 工作站開始提供約 100 人服務，建議至少先完成以下條件：

- 使用較高規格硬體
- 先做實際課堂 chatflow 壓力測試
- 設定明確的備援與重啟流程
- 課堂期間安排現場技術支援

## 11. 更新、修補與日常維護

### 11.1 更新系統

若 repo 已有新版本，可在根目錄執行：

```powershell
.\patch.ps1
```

常見模式：

```powershell
.\patch.ps1 -Mode status
.\patch.ps1 -Mode full
.\patch.ps1 -Service auth-service
```

適用情境：

- `-Mode status`：先查看是否有更新
- `-Mode full`：需要完整重建時使用
- `-Service`：只修補單一服務時使用

### 11.2 日常診斷

若教師回報「登入失敗」、「畫面卡住」或「聊天沒有反應」，第一步通常不是重裝，而是先做診斷：

```powershell
.\diagnose.ps1 -Quick
.\diagnose.ps1 -Login
```

這能幫助管理者分辨問題是在：

- Docker 未啟動
- 某個服務未啟動
- 連接埠衝突
- JWT 設定不同步
- 登入流程異常

## 12. 常見問題與注意事項

### 12.1 連接埠 8000 被其他程式占用

Bridge 前台會透過本機 `8000` 連到 Flowise Proxy。若 `8000` 被其他程式占用，例如 SSH tunnel，可能造成：

- 登入看似成功，但聊天或管理功能失敗
- 前台呼叫到錯誤的服務

遇到這種情況，應先檢查是哪個程序占用了 8000。

### 12.2 重設部署後，資料庫憑證與新設定不一致

若曾做過重設或重建，但 Docker volumes 仍保留舊資料，可能出現：

- MongoDB 或 PostgreSQL 使用舊密碼
- 新產生的 `.env` 與舊資料庫狀態不一致
- 服務啟動後出現驗證錯誤

也就是說，重設不只要清掉設定檔，還要注意資料卷是否沿用舊狀態。

### 12.3 JWT secrets 必須一致

Auth Service、Accounting Service 與 Flowise Proxy 之間需要共享一致的 JWT 驗證設定。若其中一個服務使用不同 secret，常見結果是：

- 使用者可以登入，但聊天請求被拒絕
- 額度檢查失敗
- 系統看似正常，實際上跨服務驗證失敗

### 12.4 本機郵件是測試用途

本機部署下會使用 MailHog 做測試郵件，不代表正式對外郵件服務。這表示：

- 本機部署適合測試流程
- 若要正式對外寄送郵件，仍需規劃正式 SMTP 或雲端郵件服務

## 13. 建議的角色分工

若學校要把這套系統納入教學流程，建議分工如下：

- 教師：設計課程使用方式、測試 chatflow、安排學生帳號需求
- 管理者：維護帳號、權限與額度策略
- IT 支援：維護 Docker 工作站、處理防火牆、網路與對外服務設定

這樣可避免讓教師承擔過多系統維運工作。
